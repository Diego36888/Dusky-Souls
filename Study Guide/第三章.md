## 3.1 好软件需求规格的意义（Importance of Good SRS）

### 什么是 SRS？

- **定义**：软件需求规格说明书（Software Requirements Specification, SRS）是用户需求与系统设计之间的**契约文档**。  
- **作用**：
  1. 明确系统“要做什么”，而非“怎么做”  
  2. 为设计、测试和维护提供依据  
  3. 降低沟通成本与需求歧义  

### 一份好的 SRS 应具备：

| 特性 | 说明 |
|------|------|
| 完整性 | 所有功能和约束都被描述 |
| 一致性 | 各部分不冲突 |
| 可验证性 | 可通过测试确认需求是否满足 |
| 可追踪性 | 每个需求来源清晰可追溯 |
| 可修改性 | 结构清晰，易于更新 |

> ✏️ **思考**：在项目中，一个模糊的需求说明可能造成哪些问题？

## 3.2 需求过程（The Requirement Process）

### 主要阶段：

1. **需求获取（Elicitation）**  
   - 与用户访谈、问卷、观察业务流程  
   - 产出：初步需求列表  
2. **需求分析（Analysis）**  
   - 分类、去歧义、确定优先级  
   - 输出：分析模型（DFD、用例）  
3. **需求规格化（Specification）**  
   - 编写标准化的 SRS 文档  
4. **需求验证（Validation）**  
   - 检查完整性、一致性和可行性  
5. **需求管理（Management）**  
   - 控制需求变更，保持版本一致  

---

## 3.3 需求规格（Software Requirement Specification）

### 3.3.1 软件需求规格应具备的特点

- 正确性（Correctness）  
- 无歧义性（Unambiguity）  
- 完整性（Completeness）  
- 一致性（Consistency）  
- 可验证性（Verifiability）  
- 可修改性（Modifiability）  

### 3.3.2 软件需求规格的组成

| 类型 | 内容 |
|------|------|
| 功能需求 | 系统应执行的操作 |
| 非功能需求 | 性能、可靠性、安全性、可维护性 |
| 外部接口需求 | 与硬件、外部系统交互方式 |
| 约束条件 | 法规、设计限制等 |

### 3.3.3 需求文档的结构（SRS Template）

**典型结构：**
1. 引言（目的、范围、定义）  
2. 总体描述（系统环境、用户特征）  
3. 具体需求（功能、性能、接口）  
4. 附录（数据字典、术语表）

## 3.4 用例驱动功能规格（Use Case–Driven Specification）

### 3.4.1 基础知识

- **用例（Use Case）**：系统从用户角度描述的交互行为。  
- **参与者（Actor）**：与系统交互的角色（人或系统）。  
- 每个用例包含：
  - 触发事件
  - 正常流程
  - 备选流程
  - 异常情况  

### 3.4.2 几个例子

**例：图书馆管理系统**

| 用例名称 | 借书 |
|-----------|------|
| 参与者 | 读者 |
| 主要流程 | 输入图书编号 → 系统验证 → 更新借阅记录 |
| 异常流程 | 图书不可借、超期未还 |

### 3.4.3 扩展（Extensions）

- 使用 UML 用例图展示系统行为全貌  
- 支持“扩展点”与“包含关系”以简化复杂功能  

### 3.4.4 构建用例（Building Use Cases）

1. 识别系统边界  
2. 确定主要参与者  
3. 为每个参与者定义目标与场景  
4. 用统一格式描述每个用例  
5. 校验覆盖率与一致性

## 3.5 其他分析方法（Other Analysis Techniques）

### 3.5.1 数据流图（DFD）

- 描述系统中**数据如何流动**。  
- 主要元素：
  - 过程（Process）
  - 数据流（Data Flow）
  - 数据存储（Data Store）
  - 外部实体（External Entity）  

📘 **层次化建模**：
- 一级DFD：展示主要流程  
- 二级DFD：细化某个子过程  

### 3.5.2 实体关系图（ER图）

- 用于建模系统中的数据结构与关系。  
- 组成部分：
  - 实体（Entity）
  - 属性（Attribute）
  - 关系（Relationship）

**示例：**  
“学生” 实体与 “课程” 实体 之间存在 “选修” 关系。

---

## 3.6 验证（Validation）

- **目标**：确保需求规格正确反映用户意图。  
- **常用方法**：
  - 需求评审（Review）
  - 原型验证（Prototype）
  - 模拟或场景分析（Simulation）

验证问题包括：
- 是否遗漏功能？  
- 是否存在冲突？  
- 是否具备可测性？  

---

## 3.7 小结（Summary）

| 内容 | 关键点 |
|------|--------|
| 需求过程 | 获取 → 分析 → 规格化 → 验证 → 管理 |
| SRS 特点 | 完整、一致、无歧义、可修改 |
| 功能建模 | 用例图、DFD |
| 数据建模 | ER 图 |
| 验证 | 保证需求的正确性与可行性 |

> ✅ 一份高质量的 SRS 是项目成功的基础。
