# 第7章 – 编码与单元测试


## 7.1 编码的重要性
- 编码是将设计转化为可执行程序的阶段。
- 高质量的编码直接影响：
  - 软件的可靠性与可维护性。
  - 测试与调试的效率。
- 编码阶段约占整个开发成本的 20%～30%。

---

## 7.2 编码的目标
1. **正确性（Correctness）**  
   程序必须实现设计和规格说明所要求的功能()。
2. **可读性（Readability）**  
   代码应易于他人理解和维护,减少出现需要注释解释的情况。
3. **可维护性（Maintainability）**  
   修改和扩展应方便、安全。
4. **效率（Efficiency）**  
   保证在合理资源下运行良好。

---

## 7.3 编码风格与规范
- 统一的编码风格有助于：
  - 提高可读性和可维护性。
  - 便于团队协作和代码审查。
- 常见的编码规范包括：
  - 命名规则（变量、函数、类命名清晰且一致）。
  - 注释标准（解释复杂逻辑、记录作者和修改信息）。
  - 缩进与排版（保持一致结构）。
  - 模块结构清晰，每个函数只完成一个逻辑任务。
- **代码审查（Code Review）** 是确保编码质量的重要环节。

---

## 7.4 防御式编程（Defensive Programming）
- 编程时要假设可能出现错误输入或异常情况。
- 常用做法：
  - 输入检查与验证。
  - 使用断言（assertions）检测程序状态。
  - 错误处理与异常机制。
  - 限制副作用和全局变量使用。
- 目标：让程序在异常情况下仍能保持可预测行为。

---

## 7.5 代码审查与走查（Code Review and Walkthrough）
- **代码审查（Review）：**
  - 由其他开发人员检查代码。
  - 关注逻辑错误、风格问题、潜在缺陷。
- **走查（Walkthrough）：**
  - 作者带领团队逐步解释代码实现。
  - 强调理解与学习，而非批评。
- 优点：
  - 早期发现错误。
  - 提高团队知识共享。
  - 降低测试阶段的错误修复成本。

---

## 7.6 单元测试（Unit Testing）
- **定义：** 测试软件的最小可测试单元（通常是一个函数或类）。
- **目的：** 验证单元功能正确性与逻辑完整性。
- **特点：**
  - 通常由开发人员执行。
  - 测试范围小、速度快。
- **常见内容：**
  - 输入与输出验证。
  - 边界条件检查。
  - 异常与错误处理。
- **工具：** 常用如 JUnit、CppUnit、pytest 等。

---

## 7.7 编码与单元测试的关系
- 编码与单元测试应**同时规划、交叉进行**。
- 良好的编码风格能简化测试。
- 测试结果可反过来揭示代码设计中的问题。
- 在敏捷开发中，测试驱动开发（TDD）体现了两者的结合：
  - **先写测试，再写代码。**

---

## 7.8 编码过程中的质量保证
- 编码阶段是质量控制的第一道关口。
- 关键措施：
  1. 遵循标准与最佳实践。
  2. 定期进行代码审查。
  3. 使用静态分析工具（如检查未使用变量、潜在缺陷）。
  4. 进行充分的单元测试。

---

## 7.9 常见编码错误类型
- 逻辑错误（逻辑条件不符）。
- 边界错误（循环范围、数组越界）。
- 初始化错误（变量未初始化）。
- 资源泄漏（内存、文件未释放）。
- 并发错误（多线程共享资源冲突）。

---

## 7.10 小结
- 编码阶段不仅仅是写代码，而是**构建高质量软件的核心环节**。
- 好的代码应具备：
  - 清晰、规范、可维护。
  - 具备防御性，能应对异常。
  - 经过审查与充分的单元测试。
- “**写出正确的代码**” 与 “**证明代码正确**” 同样重要。

| 术语 | 含义 |
|------|------|
| Coding | 将设计转化为可执行程序的过程 |
| Coding Standards | 编码规范与风格约定 |
| Defensive Programming | 防御式编程，提高容错能力 |
| Code Review | 他人检查代码质量 |
| Walkthrough | 作者带领团队理解代码 |
| Unit Testing | 测试最小的软件组件 |
| TDD (Test-Driven Development) | 测试驱动开发，先写测试再写代码 |
